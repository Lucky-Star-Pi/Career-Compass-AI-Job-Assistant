# 原始记录交付与脱敏审查方案

负责人及审查人：参赛者本人。最晚时点：B18开始之前完成逐份审查、交付资格判断与清单；不以B18打包时间代替审查时间。本轮仅制定方案，不制作副本、不复制或更改四份native证据。

## 交付对象和渠道

- 原件：INDEX列出的4份byte-identical native JSONL，是已冻结的完整行前缀快照；不宣称覆盖捕获后的全部对话。只供参赛者本人保管及具备合法查看权限的指定评审受控核验，不对公众开放。
- 原件交付方式：不进公开仓库；参赛者审查可交付范围后，在仓库外制作AES-256加密7z压缩包并加密文件名，包含原件及内部清单。通过赛事指定私密渠道单独提交；另交独立SHA256清单，含每个原件及压缩包的哈希、字节数、覆盖范围。密码通过独立私密渠道另行提供，不进Git、日志、提示词或本聊天。本阶段不安装压缩工具、不打包、不提供密码。
- 脱敏副本：只含可向相应接收方披露的用户提示、助手公开回复和工具执行记录。审查通过的副本及审计映射可随源码提交；如果仍涉及隐私，仅通过私密渠道交指定评审，不公开。
- 加密不是披露授权。发现系统提示词、内部指令、内部推理、第三方会话、凭据或个人信息时，不得因加密就向无权接收者交出原件或密码。不可交付的原件保持封存，按末节披露缺失。副本不得冒充原件。

## 副本审计格式

每份副本一条主记录：original_file、original_sha256、copy_file、copy_sha256、export_method=redacted-copy、reviewer（参赛者本人）、reviewed_at（ISO8601+08:00）、audience、decision。每条删改明细登记 original_line_start/end（从1计）、JSON字段路径、action、reason、替换标识；整行删除也登记原行号。保留原件SHA256→副本SHA256映射。不得将副本export_method写成native或native-byte-prefix-copy。

审查流程：逐份核对只读原件哈希→审查可披露内容→在独立位置制作副本→二次审查→计算副本哈希并填映射→决定公开/私密/不交付→制作允许交付的加密包和独立清单→在B18打包清单登记实际交付结果。本轮所有副本与包均为尚未制作，不能登记为已交付。

## 索引闭环与降级披露

manifest模板占位`pending-next-task-commit`必须在紧接着的下一次提交内消除，否则视为未完成。原始快照的任务关联指向实际任务提交；末次收尾提交本身仅由Git历史定位，避免循环。

如果B18前不能审查、不能安全提供原件、没有赛事私密渠道、加密工具或密码独立传递方式，则明确写：**原始记录未交付**。逐份列出原件文件名、哈希、已留存/未交付状态、覆盖时间、缺失区间、原因和可提供的脱敏副本范围。只交副本时写“仅脱敏副本已交付，原始记录未交付”；摘要与复盘不能顶替原件。保留审查失败和交付失败事实，不伪造审查人或时间。
